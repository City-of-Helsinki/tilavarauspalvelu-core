# T3.1 Write the reservation unit pricings input to the own pricing group

Label: BE
Blocked by: T2.2, T2.4

## Background

Most reservation units have one price with no options and no conditions. The staff form edits the active pricing
and one future pricing. This form stays, but the backend saves it to the reservation unit's own pricing group.

## Scope

- The reservation unit mutation keeps a `pricings` input. Each pricing becomes one `BASE` component with no option
  and no conditions. `valid_until` comes from the next pricing's `valid_from`.
- The backend accepts this input only if the reservation unit uses its own group (no unit group), and the group has only
  base components with no option and no conditions.
- Remove `lowestPrice` and `isActivatedOnBegins` from the input.
- Each pricing has `canApplyForDiscount`, `paymentType` and `materialPriceDescription`.
- The reservation unit query returns the same pricings, read from the components.
- The save uses the batch API rules from T2.4, so coverage errors are returned for the form.

## Acceptance criteria

- Staff can save an active and a future price with the form input.
- The input is rejected for a reservation unit that uses a shared pricing group.
