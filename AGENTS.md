# AGENTS.md

## Maintaining this file

This file uses progressive disclosure. When adding or editing an instruction,
ask "does an agent need this for *every* task, regardless of what it's working on?"

- **Yes.** It belongs in the "Always" section below, kept short and durable.
- **No, only for certain tasks.** Put the detail in a doc under `.agents/docs/`
  and add a one-line pointer to it in the "Conditional" section, stating when to read it.
- **No, and it applies to backend/frontend only.** Put it in an `AGENTS.md` in that directory,
  and add a one-line pointer to it in the "Conditional" section.

Don't restate things that are inferable by reading the code or other docs, link to them instead.
Prefer pointers to tools or commands, such as `just help`. Don't hardcode commands that can drift.

Do not edit this file or any of the conditional docs without explicit user approval.

## Scope & scale of this project

Varaamo is the public booking service of the City of Helsinki. Residents, associations, companies and city staff use it.
About 100,000 users have an active account. The service handles about 150,000 reservations per year.
The database has about 600,000 reservations in total. Helsinki residents have priority or exclusive rights to some resources,
such as seasonal bookings. This limits the user base.

Traffic is low and steady, with two known peaks. Summer cottages and saunas open once a year. This causes a spike of about one hour.
The team scales up containers by hand for it. Seasonal application rounds cause a smaller spike, mostly on the last day.
The platform is OpenShift on the City's Platta platform, with autoscaling. Use the existing caching and background task setup where it fits.
Do not add new scale patterns for load this service does not have. Guard against races where many users compete for the same slot.
Some hot paths need more complexity, such as the first reservable time of a reservation unit. Treat these as exceptions, not as the norm.

Uptime rules are loose. A deploy can take the service down for a few minutes, even during the day. Do not design for zero downtime.
A step in a runbook beats a recovery path nobody will run.

Correctness matters more than performance. Examples are payments, double bookings, access codes and personal data.
Dedicated City teams run the payment, identity and access code services. This project only integrates with them.
Still, a wrong payment state can cause a reclamation, so be careful at these integration points.

A small consultancy team builds the service on contracts of a few years. The current contract ends at the end of 2028.
Between contracts, a separate consultancy does long-term maintenance. Prefer plain, well-known Django and React patterns
that a new maintainer can read. When a pattern exists to survive a scale this service does not have, say so and take the simpler one.

## Always

- Use plain words and plain punctuation. No dashes, no semicolons, no long sentences. Where you reach for a dash, start a new sentence. Use ASD-STE100 Simplified Technical English.
- Never print, log, or persist the contents of a .env file or any secret value.
- Never use anything in backend virtualenv directly. Use `poetry run` instead.
- Never run `git checkout --`, `git restore`, `git reset --hard`, `git clean`, or any other command that discards uncommitted changes,
  on a file or directory you have not just inspected with `git diff` for that exact path. Read the full diff of every file the command would affect first.
  If a file has unstaged changes you did not make yourself in this session, stop and ask the user before discarding them.
